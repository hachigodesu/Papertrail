# Checks for 1.6.0 (step 0)

What the risky parts of 1.6.0 need, found on 18 November 2026 with throwaway probes. Nothing here is product code.

## CSL styles: citeproc-js in QuickJS-ng

**Versions:**
- **QuickJS-ng 0.17.0** (18 September 2026), from `https://github.com/quickjs-ng/quickjs/archive/refs/tags/v0.17.0.tar.gz`, SHA-256 `559bc4c420475e55c7ab4510adbc562f55d7524d75e8e89d79ce4bb02f5687d9`. 0.18.0 was under three weeks old.
- **citeproc-js 2.4.63**, from `https://registry.npmjs.org/citeproc/-/citeproc-2.4.63.tgz`, SHA-256 `7f2b7714bfd1f4480aad9c34972eb5d48dc1b85876ba21b5aa9aee74156e2ccf`. The file used is `package/citeproc_commonjs.js`, 970 KB.

**Licences:**
- citeproc-js's `LICENSE` offers the CPAL version 1 or later, or the AGPL version 3 or later. Papertrail uses it under the AGPL. Its `package.json` says "AGPL-1.0", which is a mistake there.
- QuickJS-ng is MIT, with Unicode-3.0 for its generated tables.

**Building QuickJS-ng:**
- Only `dtoa.c`, `libregexp.c`, `libunicode.c` and `quickjs.c` are needed, without `quickjs-libc.c`, so scripts have no file, process or network access.
- It builds without warnings (built with `-w`) under:
  - MSYS2's GCC 16.2
  - Arch's GCC 16.2.1
  - Ubuntu 24.04's GCC 13.3
- It needs `_GNU_SOURCE`, plus `WIN32_LEAN_AND_MEAN _WIN32_WINNT=0x0601` on Windows. On Linux it links `m`, `dl` and threads.
- The AppImage's Ubuntu 22.04 (GCC 11) is still to be tried when packaging.

**Running citeproc-js:**
- citeproc-js needs only `var module = {exports: {}}` before it, and `module.exports` is `CSL`. Its own `CSL.parseXml` takes the style as an XML string, so no DOM is needed.
- A custom output format, `CSL.Output.Formats.papertrail`, works:
  - Runs open with U+E000 and a letter (`i` italic, `I` upright, `b` bold, `B` normal weight, `c` small caps, `C` normal variant, `u` superscript, `d` subscript, `n` baseline) and close with U+E001.
  - The left margin is wrapped in U+E002 and U+E003.
  - `text_escape` removes U+E000 to U+E0FF from the input, so a title can't add markup.
- Output is identical on Windows, Arch and Ubuntu.

**Speed** (Ryzen 7 3700X, release build):

| | APA (85 KB) | MLA (44 KB) | Other styles tried |
|---|---|---|---|
| Building an engine | 6.1 s, 2.7 s with the fix below | 130 ms | 35 to 100 ms |
| Memory | about 145 MB an engine | 17.5 MB | 4 to 7 MB |

- Loading citeproc-js from source takes 27 to 40 ms. Bytecode (1.6 MB) loads in 3 ms, which isn't worth the build step, so it's loaded from source.
- The other styles tried were Nature, IEEE, AMA, Elsevier Harvard, Chicago notes and NLM.
- **Why APA was slow:** `CSL.expandMacro` finds each macro with `getNodesByName`, which walks the whole style tree. That was 22 million calls for APA.
  - A replacement installed from our own script looks only among the style's direct children, the only place CSL allows macros. It needs no cache.
  - It leaves output identical for all eight styles tried, and it cuts APA from 6.1 s to 2.7 s.
- **What's left for APA** is its 14 sort keys. Each inlines its macros, so it's 7,800 macro builds. That's how citeproc works, so it stays as it is.
- An engine is therefore kept per style, made once and reused.

**Bibliographies** grow linearly:

| 500 references | Time | Memory |
|---|---|---|
| Nature | 2 s | 7 MB |
| MLA | 9 s | |
| APA | 12 s | 215 MB |

So copying many references needs its thread and a progress message.

**In-text citations:** `previewCitationCluster` costs time in proportion to every item registered (about 65 ms for each 100 items, per citation). So an in-text citation registers only the items being cited, not the whole list.

**Hostile styles:**

| Style | Result |
|---|---|
| A macro that calls itself, or two calling each other | citeproc refuses: "would cause an infinite loop" |
| An exponential fan-out (12 levels of 4 calls) | The interrupt handler stops it at the deadline, at 83 MB |
| Not a style (HTML) | A `TypeError` |
| Half a style | **No error:** it renders `[NO_PRINTED_FORM]` |
| Entities defined in a DTD | Not expanded by `CSL.parseXml` |

So the C++ side must check a style with `QXmlStreamReader` before giving it to citeproc. A style has to be well-formed XML, with no DTD, a `style` root in the CSL namespace, and `info/id` and `info/title`.

**After an interruption or running out of memory,** the runtime is thrown away and a new one made. Out of memory reports `null` as the error, so it needs its own message.

**Styles and locales:**
- Take them from the `v1.0.2` branches: styles at `7a37c5a736c10fbd468bc31f92cbc6eafaa2173d` (2,909 independent and 7,965 dependent styles), locales at `f637c83f6267b761513bcc1cb0e95571172e768c`.
- "Vancouver" is `dependent/vancouver-nlm.csl`, whose parent is `nlm-citation-sequence`.
- The probe's made-up items rendered as expected in APA, including a case cited by citeproc as "Example Ltd v Sample, 3 Made-up Law Reports 100 (Supreme Court 2021)". Papertrail replaces a case's entry with its own legal form anyway.

## PDF copies: MuPDF 1.28.5

**Versions:** every build has MuPDF 1.28.5 (MSYS2, Arch's package, Ubuntu's and the AppImage's own build, and the Flatpak) and DjVuLibre 3.5.30.

**Books MuPDF reads** (EPUB, FB2, MOBI, XPS, CBZ):
- `fz_layout_document` lays the book out. Then each page gets `pdf_page_write` and `fz_run_page`, and `pdf_add_page` and `pdf_insert_page` add it to one `pdf_create_document`.
- The text stays text, with MuPDF's own fonts (Charis SIL) embedded as Type0.
- Page sizes are kept: A4 and 6×9 in as asked, XPS and CBZ at their own sizes.
- It works the same on Windows and Arch, and the samples' hashes were unchanged afterwards.
- **Links have to be added after every page exists.** `pdf_create_link` resolves `#page=N` at once, and fails with "cannot find page" for a page not written yet. Internal links become `#page=N`, and external ones keep their address. `fz_resolve_link` and `fz_page_number_from_location` find the target.
- The outline copies with `fz_new_outline_iterator`. Its first item needs an insert and then `prev` before going down.
- **Margins:** `fz_set_user_css` is deprecated in 1.28. Use `fz_style_document(ctx, doc, 1, css)` after opening, with `@page { margin: ... }`. 3 cm margins took a 9-page sample to 12 pages.
- No sample had links, so 1.6.0 needs a made-up EPUB with an internal and an external link.

**DjVu:**
- Pages are rendered with DjVuLibre at up to 300 dpi or the file's own resolution, then drawn with `fz_fill_image` on a page of the DjVu's size in points.
- **Words that can't be seen:** `fz_ignore_text` on the PDF device writes text in render mode 3, and MuPDF extracts it again. A Noto font from `fz_lookup_noto_font` covers it, and `fz_encode_character_with_fallback` can find another script's.
- **The font:** the whole font is embedded unless `pdf_subset_fonts(ctx, doc, 0, NULL)` is called before saving. That cut a one-page copy from 237 KB to 82 KB. What's left of the font is about 50 KB, once per document.
- **Bitonal pages** (`DDJVU_PAGETYPE_BITONAL`), from a page made with `cjb2` at 300 dpi:

  | Encoding | Image size |
  |---|---|
  | 1-bit samples, compressed with Flate by the writer (`FZ_IMAGE_RAW`, bpc 1, decode `[1 0]`) | 31 KB |
  | 8-bit grey with Flate | 34 KB |
  | MuPDF's CCITT G4 (`fz_compress_ccitt_fax_g4`) | 52 KB |

  So bitonal pages use 1-bit Flate.
- **Photo and compound pages** use JPEG at quality 85 (`fz_new_buffer_from_pixmap_as_jpeg`). On the made-up samples, Flate and JPEG were close (63 KB against 77 KB for three pages at 100 dpi). Real photographs favour JPEG.
- **The samples are photo pages:** `reader_doc.djvu` and `scanned.djvu` are both photo type. 1.6.0 needs a bitonal sample, which `cjb2` can make from a PBM.
- The probe crashed once when it freed a pixmap's samples before the image drawn from them. A pixmap made with `fz_new_pixmap_with_data` keeps pointing at the caller's memory.

## Looking up a selection: Wikimedia

All of these answered with Papertrail's own User-Agent, `Papertrail/<version> (https://github.com/hachigodesu/Papertrail)`. That fits Wikimedia's policy of a name, a version and a way to contact the project. No answer carried a deprecation or sunset header.

| Request | Answer |
|---|---|
| Wikipedia `GET /w/rest.php/v1/search/page?q=...&limit=N` | `{pages: [{key, title, description, excerpt}]}`. `excerpt` has `<span class="searchmatch">` markup, to be stripped |
| Wikipedia `GET /api/rest_v1/page/summary/{title}` | `title`, `description`, `extract` (plain text) and `type` (`standard` or `disambiguation`). A redirect's title gives its target's summary. A missing page is 404 |
| The same on `de.wikipedia.org` | Works |
| Wiktionary `GET https://en.wiktionary.org/api/rest_v1/page/definition/{term}` | An object keyed by language code (for example `en`, `it`), each a list of `{partOfSpeech, definitions: [{definition}]}`. Definitions are HTML with links. Phrases work with `_` for spaces |
| The same on `de.wiktionary.org` | 501 Not Implemented |

So definitions come only from en.wiktionary, which covers words in every language.

## What changes in the plan
- **CSL:**
  - Pin QuickJS-ng 0.17.0 and citeproc-js 2.4.63 with the hashes above.
  - Load citeproc from source, with the faster macro lookup installed from Papertrail's own script, without changing citeproc's file.
  - Keep an engine per style.
  - Register only the cited items for in-text citations.
  - Check a style in C++ first.
  - Set a 512 MB memory limit and a 10 s deadline.
  - Make a new runtime after a failure.
- **The PDF copy:**
  - `fz_style_document` for margins.
  - Links in a second pass.
  - `pdf_subset_fonts` before saving.
  - 1-bit Flate for bitonal DjVu pages and JPEG for others.
  - New samples: an EPUB with links and a bitonal DjVu.
- **Looking up:**
  - The Wikipedia search, then the summary.
  - A disambiguation page shows the search's results instead.
  - Wiktionary from en.wiktionary only.
